## What this is

A cloud dashboard for an FDM 3D printer (Kobra 2 Neo). An Arduino UNO Q gateway reads the printer's serial port, two ADXL345 accelerometers and a webcam, and publishes over MQTT with mTLS to AWS IoT Core. IoT rules write to DynamoDB and S3. A Python dashboard on ECS Fargate behind CloudFront and an ALB shows the data after a Cognito login with admin approval.

## Tech stack

- Language: Python 3.12 (no framework; the dashboard uses stdlib `http.server`), HCL (Terraform `>= 1.10`)
- Cloud: AWS `eu-west-1`: IoT Core, DynamoDB, S3, Firehose, ECS Fargate, ECR, ALB, CloudFront, Cognito, Lambda, SNS, EKS
- CI/CD: GitHub Actions. Checks run on GitHub-hosted runners. Plan, apply and deploy run on self-hosted ARC runners in EKS (`infra-runner`, `app-runner`).
- Tests: stdlib `unittest`, only for `.github/agent/`

## Commands

```bash
# Terraform: format and validate one stack, with no backend and no AWS credentials
cd <stack> && terraform fmt -check -recursive && terraform init -backend=false && terraform validate

# repo-agent unit tests (16 tests)
python3 -m unittest discover -s .github/agent/tests -v

# dashboard image (unverified locally; CI builds it on every PR)
docker build --platform linux/amd64 -t printer-dashboard:dev dashboard-app

# dashboard on a laptop (unverified): reads DynamoDB and S3 with your own AWS credentials, auth off
cd dashboard-app && pip install -r requirements.txt && python app.py   # http://127.0.0.1:8080
```

Stacks, in apply order: `bootstrap/` (manual, first time only), `Network/`, `eks-cluster-for-selfhosted-runner/`, `iot-ingest/`, `dashboard-ecs/`. Never run `terraform apply` locally. Merging to `main` applies the changed stacks through `terraform-eks.yml`, after approval on the `production` environment.

## Conventions

- Every change goes through a PR. `main` is protected.
- Terraform must pass `terraform fmt -check -recursive` and `terraform validate`. CI enforces both on PRs.
- Each stack has its own state key in the `terracotta-terraform-state` bucket. Keep stacks independent and read other stacks through data sources.
- Secrets live in SSM Parameter Store, never in code or `.tfvars`. Device certificates and keys are gitignored (`*.pem`, `*.key`, `**/certs/*`).
- Workflows that run on self-hosted runners must not run code from fork PRs.
- Do not edit the text between `<!-- STATUS:START -->` and `<!-- STATUS:END -->` in `README.md`. The `readme-status` workflow owns it.

## Gotchas

- **No Python safety net.** There is no linter, no type checking, and no tests for `dashboard-app/` or `dashboard-ecs/lambda/`. The auth code (session cookie HMAC, OAuth callback, approval tokens) is untested, so check changes to it by hand.
- **No coverage threshold.** The agent tests do not measure coverage.
- `requirements.txt` files are not pinned, and `.terraform.lock.hcl` is gitignored, so dependency and provider versions can change between runs.
- The ECS task uses the `:latest` image tag. The deploy job pushes `:latest` and forces a new deployment.
- CloudFront reaches the ALB over plain HTTP. The ALB accepts only CloudFront's prefix list plus the `X-Origin-Verify` header.
- The `README.md` "Architecture", "Repository layout" and "How to run it" sections name `eks-cluster/` and `k8s/runners/`. Those paths do not exist. Use the layout table above.
- `terraform-eks.yml` plans every stack on a PR that edits the workflow itself. The plans run on the self-hosted `infra-runner`.
